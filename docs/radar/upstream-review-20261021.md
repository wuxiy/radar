## 合入前应处理的缺口

### 1. 配置化详情仍能收进登录表单（已在临时合并预览复现）

上游只在 `content/extract.ts::extractFromUrl()` 判断请求地址是否跳到登录／注册路径。`sources/web-list.ts::fetchDetail()` 在获取配置化标题、日期或摘要时，也会读取同一响应并直接抽取正文，却没有这个判断。RSS、网页和 JSON 来源启用 `config.detail` 后，都可能调用该共享详情路径。

本机 HTTP 夹具 `/article` → 302 → `/login`：

| 路径 | 实际结果 |
| --- | --- |
| `extractFromUrl(..., {paidFallback:false})` | 返回 null，正确拒绝登录表单。 |
| `fetchDetail(..., {title:true,body:true,...})` | 接受标题 `Sign in to Example` 和 607 字符登录表单正文。 |

建议在详情响应解析标题、日期、摘要和正文之前，复用上游 `isSignInRedirect()` 判断并报明确的原文不可用错误，保持采集与预览一致。保留合法 `/register` 页面只补尾部斜杠、`/authors/` 等正常路径；不要按“密码”“登录”等正文词汇一刀切排除真实文章。Jina 渲染路径本轮未做完整运行验证，不能把直连修复等同于覆盖所有渲染路径。

### 2. 冷却行为的实际边界与现有恢复流程

源码及无外部请求的分类探针确认：

- 402，或已识别为余额／套餐耗尽的特定 429，才建立 900 秒停止状态；普通 TPM/RPM 429、401、403 不建立该状态。不要根据提交标题把它概括成“所有授权失败均冷却”。
- 停止检查在付费回执创建／新尝试之前；收到或已完成的答案仍可复用，不新增请求。已在途请求不取消，因此不是严格的全局单次探针。
- 两行业使用独立数据库，`provider.stop.llm:<model>` 同名键不会跨库共享；后台切换默认模型时需继续使用现有单次调用配置快照。
- 冷却不改变本地日预算，不自动开备用模型，不自动关闭旧拒绝告警。冷却到期只允许尝试，真正收到新答案才清理停止状态并证明恢复。
- 首次触发余额拒绝的文章仍可能按现有流程记为失败，后续文章会等待；恢复供应商访问后仍需核对并接续首次失败任务，不能承诺全部自动修复。

建议后台进一步区分“本地请求预算耗尽”与“供应商额度拒绝、冷却至某时刻”，并展示剩余等待时间。当前上游没有增加专门的冷却状态展示，该项可在核心兼容完成后处理。
